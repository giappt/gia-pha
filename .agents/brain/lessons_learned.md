# LESSONS LEARNED (SỔ TAY KINH NGHIỆM DỰ ÁN FAT)

- **Tách bạch Client Session vs Service Role Trong Xác Thực Server API Routes & Chống Nuốt Lỗi Âm Thầm (Auth SSR Client Separation & Transparent Error Exposure):** Trong Next.js App Router, `createAdminClient()` (khởi tạo qua `@supabase/supabase-js` với Service Role Key) là client độc lập không có ngữ cảnh request hay cookie của trình duyệt. Do đó, việc gọi `admin.auth.getUser()` sẽ LUÔN trả về `user: null`, khiến người dùng đăng nhập bằng Google OAuth thật bị từ chối với mã 403 Forbidden. Quy tắc sống còn: (1) Bắt buộc dùng SSR Client `createClient()` từ `@/lib/supabase/server` để đọc `auth.getUser()` dựa trên cookie `sb-*-auth-token`; chỉ dùng Service Role Key để query dữ liệu vượt rào RLS; (2) Tuyệt đối không cho phép cookie dev giả lập (`fat_dev_users`) đè lên CSDL Supabase thật khi đã có kết nối DB; (3) Trên giao diện (`AdminUsersPage`), cấm dùng cú pháp `r.ok ? r.json() : { data: [] }` vì nó âm thầm biến lỗi 403/500 thành mảng rỗng khiến người dùng tưởng mất hết dữ liệu (0/0 tài khoản); bắt buộc bắt mã lỗi và hiển thị Alert Banner đỏ cảnh báo người dùng ngay lập tức.
- **Next.js Dev Chunk 404 & Build Invalidation Loop:** Khi đang mở trình duyệt xem Web ở chế độ dev (`next dev`) mà ở Terminal ta chạy lệnh `npm run build` (lệnh kiểm chứng Tầng 1) hoặc restart Next.js, thư mục `.next/static/chunks/` bị dọn sạch và sinh lại với các mã hash mới. Tab trình duyệt cũ (kết hợp Service Worker PWA `sw.js` và HMR) vẫn gửi request tìm kiếm các file chunk mang mã hash cũ (`layout.css?v=...`, `main-app.js`, `page.js`), dẫn đến hàng loạt log `GET /_next/static/... 404`. Giải pháp chuẩn xác: (1) Hard Refresh trên trình duyệt bằng tổ hợp phím `Ctrl + Shift + R` (hoặc `Ctrl + F5`) để nạp lại HTML mang bundle hash mới nhất; (2) Sinh đầy đủ các asset tĩnh trong `public/` (như `public/icons/icon-192x192.png` và `badge-72x72.png`) để Service Worker không bị 404 khi cài đặt PWA; (3) Bỏ qua request nội bộ `/.well-known/appspecific/com.chrome.devtools.json` vì đây là hành vi tự động của Chrome DevTools (bản 128+) thăm dò extension, hoàn toàn vô hại.
- **Windows PowerShell Execution Policy & Node Tooling:** Khi chạy lệnh `npm` hoặc `npx` trên môi trường PowerShell Windows có execution policy chặn script (`npm.ps1`), bắt buộc sử dụng `npm.cmd` và `npx.cmd` để chạy lệnh thành công và ổn định mà không bị lỗi `PSSecurityException`.
- **Global Workflows & 2-Way Registry Sync:** Khi bổ sung lệnh Global mới (`/g-*`), bắt buộc phải đăng ký 2 chiều vào `AGENT_ARCHITECTURE.md` (§2 danh sách lệnh & §5 bảng quyết định) và cập nhật `g-help.md` để luôn thỏa mãn bài kiểm tra toàn vẹn Bước 3b của `/g-health`.
- **0-Token Context Monitoring & Local Extensions:** Không dùng LLM prompt để tự đo context window (tránh hiệu ứng Observer Effect làm phình token); giải pháp chuẩn native là xây dựng Local Extension VS Code (`~/.antigravity-ide/extensions/`) đọc session log trực tiếp từ disk và hiển thị qua StatusBarItem.
- **Public Extension Decoupling:** Khi đóng gói công cụ hoặc extension phát hành công khai (Marketplace/Open VSX), bắt buộc phải tách rời (decouple) các lệnh nội bộ cá nhân (như `/g-compact`) thành các chỉ dẫn ngữ cảnh phổ quát (ví dụ: "Prompt AI to summarize state and start a new session") để bất kỳ người dùng nào cũng hiểu và áp dụng được.
- **Marketplace Icon Design:** Icon cho các tiện ích developer tooling trên Marketplace cần theo phong cách phẳng (Flat design), tối giản hiện đại (Swiss design style) với biểu tượng đo tiến độ vòng cung (circular progress gauge), màu gradient tinh tế trên nền squircle tối màu để tạo cảm giác chuyên nghiệp, không dùng hiệu ứng 3D neon quá rườm rà.
- **Anti Box-in-Box UI & Fresh Jade Heritage Design:** Trong thiết kế giao diện phả hệ/văn hóa số, tuyệt đối tránh lối mòn "lồng hộp" (box-in-box: thẻ bọc khối icon vuông bọc viên thuốc tag) và các gam màu nâu đất/hổ phách u tối dễ gây cảm giác đình chùa cũ kỹ; thay vào đó, áp dụng phong cách "Modern Vietnamese Heritage": nền trắng sứ với quầng sáng ngọc bích (Jade Emerald `#059669`), đường kẻ hairline siêu mảnh 1px (`border-slate-200/60`), icon nổi tự do và typography Be Vietnam Pro phân cấp rõ ràng để tạo cảm giác trang trọng, thanh thoát và tràn đầy sinh khí.
- **Offline Resilient Dev Auth & Server-First State:** Khi môi trường mạng chặn Google OAuth / external endpoints, không để client-side gọi `supabase.auth.getUser()` vô hạn định (gây treo UI ở trạng thái Loading). Giải pháp chuẩn: (1) Fast-check sự tồn tại của auth cookie trước khi gọi network; (2) Thiết lập Server Component (`Navbar.tsx`) lấy session trên server và truyền `initialUser`/`initialProfile` xuống client để render tức thì 0ms; (3) Dùng link trực tiếp `/api/auth/dev-login?action=login` set cookie dev (`httpOnly: false`) để bypass hoàn toàn OAuth mạng ngoài mà không cần đợi client JS hydration.
- **Thiên văn Âm lịch Hồ Ngọc Đức & Quy đổi `lunarYear`:** Khi chuyển đổi Dương lịch sang Âm lịch Việt Nam UTC+7, phép so sánh `monthStart` với tháng 11 âm lịch `a11` phải gán `lunarYear = year` (nếu `a11 >= monthStart`) và chỉ trừ 1 năm khi `lunarMonth >= 11 && diff < 4` (giai đoạn trước Tết Nguyên Đán). Tránh nhầm lẫn gán `year - 1` ngay từ đầu khiến các ngày đầu năm âm lịch (như Mùng 3 Tết 19/02/2026) bị lùi sai thành năm trước.
- **Kinship Engine - Tách rời Trưởng/Thứ vs Tuổi đời theo Vùng miền:** Phong tục miền Bắc và miền Trung coi trọng thứ bậc nhánh (vai Bác luôn là Anh/Chị dù ít tuổi hơn); ngược lại miền Nam ưu tiên tuổi đời thực tế (`birth_year`/`birth_date`). Khi thiết kế hàm xưng hô họ hàng, hàm so sánh cùng thế hệ (`resolveSameGeneration`) bắt buộc phải dùng bộ so sánh tuổi đời thuần túy (`compareAge`) cho miền Nam, tách biệt khỏi `compareSeniority` (vốn ưu tiên nhánh trưởng `is_senior_branch` lên đầu).
- **Lạm dụng `browser_subagent` gây cháy quota:** 4 lần gọi liên tiếp mà chưa verify bằng `curl` trước → 429 quota exhausted. Quy trình đúng: (1) curl API xác nhận response đúng, (2) sửa hết bug client-side, (3) gộp toàn bộ kịch bản vào 1 lần gọi browser duy nhất.
- **Khởi tạo state `'use client'` từ mock data:** Select box trống khi chỉ dùng `useEffect` fetch API vì React render trước khi fetch xong. Giải pháp: import trực tiếp `MOCK_CLAN_MEMBERS` để khởi tạo `useState(INITIAL_MEMBERS)` tức thì, đồng thời fetch API để đồng bộ dữ liệu mới nhất.
- **Zero-Latency In-Memory Kinship Calculation & Middleware Bypass:** Đối với các tính toán đồ thị/toán học thuần túy (như LCA & Xưng hô 3 miền), không phụ thuộc vào network `fetch('/api/kinship')` cho mọi tương tác UI vì Next.js middleware gọi `supabase.auth.getUser()` gây nghẽn 15–35s khi mạng chập chờn. Giải pháp chuẩn: (1) Tính toán in-memory trực tiếp trên client bằng các Pure Functions (`findLowestCommonAncestor`, `resolveKinshipTerms`) đạt tốc độ tức thì (< 1ms); (2) Bổ sung `api/kinship` vào matcher exclusion của `src/middleware.ts`; (3) Thiết lập Live Reactivity tự động tính lại ngay trên `onChange` của dropdown và tab vùng miền, đồng thời auto-clean ô tìm kiếm khi click nút kịch bản mẫu.
- **Xung đột giữa `next dev` và `next build` trên thư mục `.next/`:** Khi tiến trình `npm run dev` đang chạy ngầm, việc thực thi lệnh kiểm thử `npm run build` trong cùng workspace sẽ ghi đè và xóa các chunk phát triển trong `.next/server/`, khiến dev server bị sập với lỗi `Server Error: Cannot find module './xxx.js'`. Quy tắc xử lý: Bất cứ khi nào chạy `next build` để kiểm chứng Tầng 1, bắt buộc phải tự động khởi động lại (restart) dev server để nạp lại bundle dev sạch.
- **Trực Hệ Dọc vs Cây Chữ V & Đường nối vuông góc 90 độ:** Khi vẽ quan hệ gia phả trực quan, cần tách biệt rõ 2 mô hình biểu diễn: (1) Quan hệ trực hệ dọc (Cha-Con, Ông-Cháu) phải vẽ trên 1 trục đứng duy nhất (`#direct-lineage-tree`), tuyệt đối không ép vào cây chữ V 2 nhánh để tránh lặp LCA máy móc và tránh nhãn thừa `(Trực hệ từ LCA)`; (2) Quan hệ họ hàng rẽ nhánh chữ V (`#inverted-v-tree`) nên dùng hệ trục đường nối vuông góc nét liền (`solid orthogonal lines`) đồng bộ theo CSS Grid 2 cột thay vì SVG tọa độ cố định, vừa đảm bảo vuông vắn 90 độ vừa tự động co giãn thẳng hàng 100% theo tâm của thẻ node.
- **Tách bạch Danh xưng Ngữ cảnh & Cài đặt Vùng miền Dòng họ:** Không nên bắt người dùng chọn tay vùng miền tràn lan trên trang tra cứu khi dòng họ đã có quy ước mặc định trong Cài đặt (`clan_settings`); đồng thời kết quả xưng hô cần tách bạch rõ giữa danh xưng lễ nghi trong họ tộc (tôn ti theo chi nhánh) và giao tiếp thường nhật (thân mật theo tuổi tác), kèm hướng dẫn thực hành Xưng - Gọi cụ thể để người dùng biết cách xưng hô chính xác trong đời sống.
- **Chống Lạm Dụng Browser Subagent Cho Tinh Chỉnh UI Nhỏ (Anti-Tool Abuse):** Tuyệt đối không giao các kịch bản kiểm thử quá dài dòng gồm nhiều thao tác cuộn/gõ phím/click pixel liên hoàn cho `browser_subagent` khi chỉ thực hiện các thay đổi UI tĩnh (xóa thẻ JSX, đổi text, ẩn badge có điều kiện). Việc này khiến subagent rơi vào vòng lặp trial-and-error (cuộn, tìm kiếm, click lặp lại tới 90 bước), gây lãng phí tài nguyên và thời gian nghiêm trọng. Quy tắc thực tế: Chỉ cần typecheck và unit test sạch 100%, sau đó mời trực tiếp User UAT bằng mắt khi User đã mở sẵn trình duyệt tại trang đó.
- **Minh Bạch Hóa Từ Điển Xưng Hô & Tùy Biến Gia Tộc 2 Chiều:** Không để các tùy chọn cấu hình văn hóa ở dạng "hộp đen" mù mờ (như chỉ có 3 nút radio vùng miền trừu tượng). Phải minh bạch hóa bằng bảng danh mục chi tiết 16 mối quan hệ cốt lõi (Trực hệ, Cùng thế hệ, Bác/Chú/Cô, Họ hàng lệch đời) kèm tính năng chỉnh sửa trực tiếp 2 chiều (A gọi B / B gọi A). Cấu hình tùy biến được lưu dưới dạng `JSONB` trong `clan_settings.custom_kinship_dictionary` và được lõi Kinship Engine ưu tiên nạp động, vừa giữ vững phong tục vùng miền gốc vừa đáp ứng trọn vẹn tập quán xưng hô riêng biệt của từng dòng họ.
- **Cấu Trúc Thân Tộc Việt Nam Toàn Diện (Nội - Ngoại & Dâu - Rể):** Hệ thống xưng hô gia phả chỉ thực sự chuẩn phong tục khi bao phủ đủ 6 chiều quan hệ: (1) Trực hệ nội/ngoại; (2) Cùng đời ruột, họ & dâu/rể; (3) Bác/Chú/Cô bên nội và phu thê (Thím, Dượng nội); (4) Cậu/Dì bên ngoại và phu thê (Mợ, Dượng ngoại); (5) Dâu/Rể thế hệ con cháu; (6) Bậc họ hàng lệch đời. Khi danh mục mở rộng lên 32+ quan hệ, UI bắt buộc trang bị Filter Chips phân nhóm kết hợp ô tìm kiếm tức thì 0ms để tránh tình trạng cuộn trang dài gây mỏi mắt.
- **Code-First Verification Loop & Loại Bỏ Triệt Để Browser Subagent Cho Thẩm Định UI:** Kiểm chứng phần mềm bắt buộc phải lấy mã nguồn và Test Code tự động (`tests/*.test.ts`) làm chân lý thực nghiệm. Mọi logic, thuật toán toán học (LCA, Can Chi, Tree Layout tọa độ) hoặc API DTO mapping phải được chứng minh bằng log `npm test` PASS 100% trên terminal. Tuyệt đối cấm dùng `browser_subagent` để mò mẫm hay làm thay User việc kiểm thử giao diện; 100% việc nghiệm thu thị giác (màu sắc, layout, canvas pan/zoom, responsive) được trao trọn vẹn cho User (Human UAT) trên màn hình trình duyệt thực tế.
- **Tính Nhất Quán Giữa Hạ Tầng Test & Thượng Nguồn Spec:** Khi yêu cầu mọi tính năng phải có Test Code, bắt buộc phải đồng bộ 3 mắt xích: (1) `package.json` dùng wildcard `tests/*.test.ts` để tự động quét mọi file test mới; (2) Thượng nguồn `/feature-spec` chia rõ Mục 7 thành Automated Test Suite (`tests/`) và Human Visual UAT; (3) Lệnh `/feature-code` bắt buộc viết test song hành và cấm tick `[x]` nếu log test chưa chạy qua file test mới.
- **Kỷ Luật Công Cụ & Ngoại Lệ 'Read-Once':** Quy tắc chống lạm dụng công cụ 'Read-once' ở tầng Global cần gắn kèm ngoại lệ rõ ràng: cho phép đọc lại khi file vừa được chỉnh sửa bằng tool edit hoặc lệnh terminal để xác minh kết quả, ngăn AI hiểu máy móc mà từ chối kiểm tra lại file vừa can thiệp.
- **Hệ Thống Anchor ID `[R-*]` & Di Cư Hệ Gen (Genetic Migration):** Khi đồng bộ Global xuống Local qua `/g-pull`, việc dùng số thứ tự sẽ làm gãy tham chiếu chéo do Local có xen kẽ các luật riêng dự án. Giải pháp chuẩn là gắn Anchor ID bất biến `[R-*]` trên từng đề mục; `/g-pull` merge theo ID thay vì theo số thứ tự, bảo toàn 100% luật dự án và triệt tiêu vĩnh viễn nguy cơ tham chiếu sai mục.
- **Quy ước Hôn nhân nội tộc & Ghost Node (Directional Ghost Node Policy):** Khi hai thành viên nội tộc cưới nhau (ví dụ: Tuấn Chi 1 lấy Mai Chi 2), nếu không quy ước chiều rẽ thì cả hai nhánh đều nhận diện phối ngẫu và sinh Ghost Node gây trùng lặp ($28 + 2 = 30$ thẻ). Dựa trên tập quán truyền thống Việt Nam (người nữ theo họ chồng), thuật toán dàn trang quy ước: Người vợ hiển thị dạng `GhostNode` duy nhất bên cạnh chồng tại nhánh của chồng (trỏ ngược về ID gốc ở Chi 2); còn tại nhánh cha mẹ người vợ, cô ấy xuất hiện như con gái ruột và không kéo chồng sang làm rể. Quy tắc này đảm bảo tổng số node trên Canvas luôn là $N + 1$ thẻ chuẩn xác.
- **TypeScript Interface Extensibility cho `@xyflow/react` v12:** Trong React Flow 12, generic `Node<Record<string, unknown>>` yêu cầu kiểu `data` phải có index signature hoặc kế thừa `Record`. Khi khai báo các DTO Node Data cho Canvas (như `TreeNodeData`, `GhostNodeData`), bắt buộc phải cho `extends Record<string, any>` để các hooks `useNodesState<Node<TreeNodeData>>` và `nodeTypes` hoàn toàn tương thích và compile sạch 0 lỗi TypeScript.
- **Zero Node Overhead qua Virtual Relative Handle & Đường Nối Vuông Góc 90°:** Khi thiết kế cây phả hệ trong `@xyflow/react` cần nhánh con cái xuất phát từ trung điểm khoảng trống giữa 2 vợ chồng, nếu chèn dummy/joint node trung gian vào đồ thị sẽ làm phình to DOM và làm sai lệch số lượng node của dòng họ (gãy Unit Tests `nodes.length`). Giải pháp chuẩn mực là sử dụng **Virtual Relative Handle**: đặt Handle con cái tại đáy thẻ Chồng ở tọa độ tương đối `style={{ left: '210px' }}` (`id="children-joint"` — tương ứng đúng tâm điểm khoảng hở $20\text{px}$ giữa Chồng $200\text{px}$ và Vợ $200\text{px}$). Kết hợp cạnh con cái `type: 'step'` vuông góc $90^\circ$ dứt khoát và cạnh hôn phối `type: 'straight'` nối ngang phẳng phiu giữa 2 hông (`spouse-right` $\rightarrow$ `spouse-left`), giao diện phả đồ đạt chuẩn mực trang trọng, loại bỏ hoàn toàn đường xiên chéo $45^\circ$ mà số lượng node giữ nguyên $100\%$ ($0$ node phát sinh).
- **Invisible Handle Styling & Khung Chữ T Nét Liền Đồng Bộ (`┴`):** React Flow mặc định render các chấm tròn màu xám/đen tại các điểm Handle gây mất mỹ quan phả đồ. Giải pháp triệt để là áp dụng CSS tàng hình toàn diện: `className="!opacity-0 !w-0 !h-0 !border-0 !p-0 pointer-events-none"` cho 100% handles. Đồng thời, đặt handle con cái tại `top: 48px, left: 210px` (trung điểm thanh ngang hông nối vợ chồng) kết hợp đồng bộ màu xanh ngọc bích `#059669` và nét liền (`type: 'straight'`), tạo thành kết cấu chữ T ngược (`┴`) vuông vức $90^\circ$ liền mạch, không còn bất kỳ dấu chấm lem nhem nào trên canvas.

- **Tuân Thủ Quy Tắc Bất Biến Của React Hooks & Rào Chắn Sau Return (React Rules of Hooks & Zero Hook After Return Guard):**
  1. *Cơ chế Linked List của React Fiber:* React quản lý hooks theo thứ tự tuần tự trong danh sách liên kết đơn (Linked List). Số lượng và thứ tự gọi hook trong component phải tuyệt đối bất biến giữa mọi lần render.
  2. *Căn nguyên lỗi `Rendered more hooks than during the previous render`:* Đặt hook (như `useEffect`) sau một câu lệnh early return (`if (!isOpen) return null;`) sẽ khiến số lượng hook bị lệch: lúc modal đóng chỉ duyệt $N$ hooks trước return, lúc modal mở lại duyệt $N + 1$ hooks, dẫn đến crash runtime trên trình duyệt.
  3. *Quy tắc khai báo & Rào chắn nội bộ:* 100% hooks phải được khai báo ở đầu component trước câu lệnh `return`. Nếu logic trong hook phụ thuộc vào điều kiện mở (`isOpen`), đặt guard `if (!isOpen) return;` vào bên trong callback của effect, tuyệt đối không di dời vị trí khai báo hook.
  4. *Rào chắn kiểm thử tự động (Static AST/String Guard):* Bổ sung test tự động quét mã nguồn các component modal (`TC_UT_ZERO_HOOK_AFTER_RETURN_GUARD`) để phát hiện và chặn đứng ngay từ vòng CI nếu có bất kỳ hook nào được định nghĩa sau câu lệnh early return.

- **Cơ Chế Gỡ Con Khỏi Cha Mẹ & Ràng Buộc Toàn Vẹn Hôn Phối Cascading (Child Unlink & Cascading Parent Coupling):**
  1. *Gỡ con an toàn không làm mất dữ liệu (Soft Disconnect to Unlinked Tray):* Khi sửa hồ sơ người cha hoặc người mẹ, việc gán nhầm con phải có nút thao tác gỡ ngay tại chỗ (`UserMinus` / Hủy liên kết) với cơ chế Staged Unlink (gạch mờ + Hoàn tác).   2. *Mở khóa chọn Cha Mẹ trong chế độ chỉnh sửa (`mode === 'edit'`):* Tránh bẫy logic khi dùng cờ `defaultRole !== 'child'` để ẩn dropdown Bố Mẹ khi tạo mới nhưng lại vô tình khóa luôn quyền chọn Bố Mẹ khi sửa thành viên. Điều kiện chuẩn mực là `(mode === 'edit' || defaultRole !== 'child')`.
  3. *Tự động đồng bộ Mẹ theo Cha (1-Click Cascading Auto-Sync):* Trong phả hệ, một đứa con bắt buộc phải thuộc về một cuộc hôn nhân xác thực. Khi người dùng đổi Cha ruột:

     - Nếu Cha mới có nhiều vợ $\rightarrow$ Reset Mẹ và dropdown Mẹ chỉ lọc ra các bà vợ của Cha mới, ngăn chặn tuyệt đối việc gán Bố A lấy Mẹ B không phải vợ chồng.
  4. *Rào chắn toàn vẹn hôn phối trước khi lưu (Spouse Integrity Guard):* Trước khi submit form, kiểm tra cặp `[fatherId, motherId]` có tồn tại trong `spouse_relations` hay không. Nếu không, chặn lưu và thông báo lỗi rõ ràng để bảo đảm tính liêm chính của đồ thị cây.

- **Gỡ Con Cấp Gia Đình (Family-level Soft Disconnect), Opt-Out Con Riêng & Nối Phả Chuẩn Giới Tính (Edge Case 38):**
  1. *Căn nguyên lệch pha giữa Profile và Canvas khi gỡ con:* Trong CSDL và đồ thị cây, layout gom con theo cụm gia đình (`parent + spouse`).   2. *Giải pháp chuẩn hóa phối hợp 2 tầng:*
     - *Tầng 1 (Tái chuẩn hóa vector trong viewBox):* Mở rộng độ phủ chiều cao của vector path lên $\mathbf{88.0\%}$ trong viewBox $100 \times 100$ ($Y \in [6.0, 94.0]$, $X \in [14.8, 85.2]$), căn giữa hoàn hảo tại $(50.0, 50.0)$. Chữ thư pháp hiển thị to rõ, khoáng đạt, sắc nét tuyệt đối mà vẫn giữ khoảng đệm thoáng đãng và trang nhã.

- **Auto-Save Trên Toggle Switch & Lỗi Âm Thầm Từ Chối Cập Nhật RLS Supabase (Toggle Auto-Save & Server RLS Mutation):**
  1. *Lỗ hổng UX khi không có Auto-Save trên công tắc Switch:* Trong thiết kế trang Cài đặt/Quản trị, người dùng có thói quen gạt công tắc switch là kỳ vọng cài đặt có hiệu lực tức thì (tương tự iOS Settings hay Vercel/Cloudflare Dashboard). Nếu chỉ gán `onChange` cập nhật React State trong bộ nhớ RAM và bắt người dùng phải cuộn xuống tận đáy trang để bấm nút "Lưu", người dùng sẽ dễ dàng bỏ qua, dẫn đến việc không có request HTTP nào được gửi đi khi họ chuyển tab/cửa sổ để kiểm tra.   2. *RLS Silent Failure khi gọi Mutation bằng Client SSR trong môi trường Dev:* Khi gọi `supabase.from('table').update()` bằng client SSR `createClient()`, nếu trong môi trường phát triển đang dùng tài khoản Dev Bypass (không có JWT Supabase thật trong Authorization header), Supabase sẽ thực thi truy vấn với vai trò khách vãng lai (`anon`). Cơ chế Row Level Security (RLS) của PostgreSQL sẽ âm thầm từ chối lệnh UPDATE (trả về `{ data: [], count: 0 }` mà không ném ra exception). Hậu quả là server chỉ ghi cookie fallback cho riêng trình duyệt đó; khi mở Cửa sổ Ẩn danh (Incognito), trình duyệt ẩn danh không có cookie và đọc trực tiếp từ DB Postgres nơi dữ liệu chưa từng được cập nhật.
  3. *Quy tắc bắt buộc đối với API Mutation trên Server:* Mọi thao tác ghi dữ liệu (INSERT/UPDATE/DELETE) trong Server API Routes (`/api/*`) sau khi đã xác thực quyền Admin bắt buộc phải sử dụng `createAdminClient()` (Service Role Key) để bypass RLS, đảm bảo dữ liệu ghi trực tiếp vào PostgreSQL thật 100%. Đồng thời, phải cập nhật/làm tươi ngay cookie cache (`fat_feature_flags_cache`) trong cùng response để triệt tiêu độ trễ của bộ đệm Middleware.

- **Cơ Chế Đăng Xuất Toàn Diện Đa Tầng (Full-Spectrum Dual-Layer Logout Engine):**
  1. *Anti-Pattern gán cứng Link Dev cho hành động Auth cốt lõi:* Tuyệt đối không hard-code các thẻ link `<a>` trỏ vào endpoint dev (như `/api/auth/dev-login?action=logout`) cho các nút hành động hệ thống quan trọng như Đăng xuất. Việc này phá vỡ vòng đời ứng dụng và bỏ qua hàm xử lý `onClick={handleLogout}`.
  2. *Cơ chế Đăng xuất 2 Tầng (Client + Server):* Trong ứng dụng SSR (Next.js App Router + Supabase SSR), đăng xuất an toàn bắt buộc phải phối hợp cả 2 tầng:
     - **Tầng Client (Browser):** Gọi `await supabase.auth.signOut()` để dọn sạch JWT tokens trong LocalStorage / Cookie trình duyệt, đồng thời reset state component trong React (`setUser(null)`).
     - **Tầng Server (API Route `/api/auth/logout`):** Gọi `const supabase = createClient(); await supabase.auth.signOut();` để thu hồi phiên trên Supabase backend và xóa các cookie HTTP-only (`sb-*-auth-token`). Đồng thời xóa toàn bộ cookie giả lập dev (`fat_dev_user`) và cookie cache (`fat_feature_flags_cache`).
  3. *Hard Navigation sau Đăng xuất:* Thay vì dùng `router.push('/')` (chỉ cập nhật router client-side và có thể để lại state cũ của Server Components), bắt buộc sử dụng `window.location.href = '/'` để kích hoạt hard reload toàn bộ ứng dụng, buộc RootLayout và Middleware đánh giá lại từ đầu quyền truy cập của Guest.

- **Thực Thi Toàn Diện Cờ Tính Năng & Chống Lỗi Cờ Bất Hoạt (Full-Spectrum Feature Flags Enforcement & Dead Flags Prevention):**
  1. *Căn nguyên "Cờ Bất Hoạt" (Dead Flags Anti-Pattern):* Việc lưu trữ thành công các cờ tính năng trong CSDL hoặc trang cấu hình Admin (`/admin/features`) hoàn toàn vô nghĩa nếu các thành phần điều hướng (`Navbar`, `MobileBottomNav`), giao diện trình diễn (`HomePage` Spotlight), và cổng kiểm soát truy cập (`auth-gate`, `middleware`) không thực sự tiêu thụ (consume) và ràng buộc các giá trị cờ đó. Khi gạt cờ OFF, giao diện vẫn trơ trơ hiển thị khiến người dùng hiểu lầm rằng tính năng bị hỏng.
  2. *Mô Hình Đồng Bộ Cờ Tính Năng 3 Tầng (Three-Tier Enforcement Strategy):*
     - **Tầng Điều Hướng (Navigation Layer):** `RootLayout` đọc `featureFlags` từ cookie cache/DB và phân phối xuống `Navbar` và `MobileBottomNav`. Cả hai component lọc bỏ các tab/link (`/anniversaries`, `/kinship`) khi cờ bị tắt, trừ khi người dùng là `Super Admin` (được giữ quyền bypass để truy cập hiệu chỉnh dữ liệu & từ điển xưng hô).
     - **Tầng Trình Diễn (Presentation Layer):** Trên `HomePage`, các khối spotlight hoặc widget liên quan (như khối Spotlight "Ngày Giỗ Gần Nhất") bắt buộc bọc điều kiện kiểm tra `featureFlags.enable_anniversaries`, tự động ẩn sạch sẽ khi cờ bị tắt mà không làm vỡ khoảng cách dòng hay bố cục flexbox.
     - **Tầng Rào Chắn Server (Server Auth Gate Layer):** Hàm pure function `evaluateAuthGate` và `middleware.ts` kiểm tra cờ đối với các truy cập trực tiếp (qua bookmark hoặc gõ URL thanh địa chỉ). Người dùng thông thường cố tình vào route bị tắt sẽ được redirect 307 an toàn về trang chủ (`/`), triệt tiêu hoàn toàn rủi ro lộ giao diện dở dang.
- **Động Cơ Tiền Tố Danh Xưng Tiền Nhân & Tối Ưu Định Dạng Ngày Giỗ (Deceased Honorific Engine & Clean Date Architecture):**
  1. *Triệt tiêu hậu tố "(Dương lịch)" thừa thãi:* Khi hiển thị ngày trên giao diện người dùng, việc kèm theo chữ `(Dương lịch)` hay `(Dương Lịch)` vừa gây rườm rà vừa dễ làm rớt dòng/tràn viền trên màn hình điện thoại di động (375px). Chỉ cần hiển thị đầy đủ Thứ và ngày tháng năm Dương lịch trang nhã (`Thứ Ba, ngày 22/09/2026`), kết hợp dòng Âm lịch nổi bật phía dưới (`Âm lịch: Ngày 12/08 (Bính Ngọ)`), người dùng lập tức phân biệt rõ ràng mà không cần thêm bất kỳ từ ngữ giải thích nào.
  2. *Quy tắc phân cấp thế hệ từ đáy lên (Bottom-up Generation Hierarchy) cho Khách / Chưa liên kết node:*
     - Khi người xem chưa liên kết tài khoản với cây gia phả, họ không có tọa độ cá nhân để xưng hô. Lúc này, xưng hô phải quy về góc nhìn tôn kính chung của con cháu dòng họ.
     - Thuật toán xác định $G_{max} = \max_{m \in members} (m.generation\_level)$ (thế hệ con cháu nhỏ nhất). Với người mất ở thế hệ $g$, độ sâu từ đáy lên là $k = G_{max} - g + 1$:
       - $k \ge 4$ (Đời thứ 4 từ dưới lên và các đời tiền nhân trên nữa): Tiền tố trang trọng bắt buộc là **"Cụ"** (VD: *Cụ Phạm Kim Đức*).
       - $k \in \{2, 3\}$ (Đời thứ 3 và thứ 2 từ dưới lên): Phân định theo giới tính: Nam $\rightarrow$ **"Ông"**, Nữ $\rightarrow$ **"Bà"** (VD: *Ông Phạm Văn Bảy*, *Bà Lê Thị Nhân*).
       - $k = 1$ (Đời đáy): Tiền tố rỗng `""` (hiển thị nguyên tên con cháu để tránh xưng hô nghịch lý).
  3. *Zero-Latency Kinship Integration khi ĐÃ liên kết node (`viewerMemberId`):*
     - Việc tính toán xưng hô theo node người xem **hoàn toàn không làm phức tạp hệ thống** và không gây trễ giao diện: Thuật toán tìm Gốc Gần Nhất (LCA) duyệt ngược cây gia phả ($h \le 15$) hoàn toàn trong bộ nhớ RAM ($O(h)$), tốn ít hơn $0.02\text{ms}$ cho mỗi người mất. Với $1 \sim 10$ người giỗ trong 30 ngày, tổng thời gian tính toán $< 0.2\text{ms}$ CPU, $0\text{ms}$ độ trễ mạng.
     - Khi có `viewerMemberId`: Hệ thống ưu tiên trích xuất danh xưng thân tộc theo ngôi của người xem (VD: `Bà nội`, `Ông nội`, `Cụ`) để ghép thẳng vào tên (`Bà nội Lê Thị Nhân`, `Cụ Phạm Kim Đức`), kết hợp huy hiệu quan hệ thân mật (`Bà nội của bạn`, `Cụ tổ của bạn`), mang lại trải nghiệm cảm xúc ấm cúng và cá nhân hóa sâu sắc cho từng con cháu trong dòng tộc.

- **Nguyên Tắc Never Locked Out & Cơ Chế Đóng Vai Nghiệm Thu (Role Impersonation Architecture):**
  Khi xây dựng tính năng cho phép Super Admin đóng vai (impersonate) các vai trò khác (như guest, viewer, claimed_member, branch_editor) để kiểm tra giao diện thực tế và chính sách quyền riêng tư (che mờ số điện thoại, ẩn nút sửa, ẩn nút claim), có 3 nguyên tắc bất biến bắt buộc phải tuân thủ:
  1. *Phân tách tầng giao diện (Presentation Layer) vs Tầng bảo mật thật (Security Layer):* Chế độ đóng vai chỉ được lưu ở Client State / Cookie (fat_impersonated_role) để điều khiển giao diện hiển thị. Ở tầng Backend API và Database, quyền thật của người dùng vẫn là super_admin, bảo đảm không bao giờ bị hạ thấp hoặc gây lỗ hổng leo thang quyền (resolveEffectiveRole chỉ cho phép super_admin thật được đóng vai, chống giả mạo quyền).
  2. *Nguyên tắc Never Locked Out:* Dù đang đóng vai vai trò có quyền hạn thấp nhất (guest), giao diện bắt buộc phải luôn duy trì một thanh Banner nổi trên đỉnh màn hình (RoleImpersonationBanner) chứa lối vào Quản Trị ([Vào Quản Trị] -> /admin/roles) và nút [Thoát Đóng Vai]. Super Admin không bao giờ bị mắc kẹt hoặc tự khóa mình khỏi trang điều hành.
  3. *Middleware Super Admin God Mode Bypass:* Middleware không được dựa vào user_metadata vốn có thể khuyết thiếu trên token OAuth của bên thứ ba, mà phải nhận diện trực tiếp Super Admin (qua email/ID) để miễn nhiễm khỏi mọi rào cản cờ tính năng (evaluateAuthGate), bảo đảm Admin luôn truy cập thông suốt mọi ngóc ngách của hệ thống.

- **Đồng Bộ Dữ Liệu Thực Tế Cho Kinship Engine & Chuẩn Hóa Schema Cột Thế Hệ (`generation_level` vs `generation_number`):**
  1. *Căn nguyên lỗi ngầm Database (Silent Fallback Trap):* Trong PostgreSQL Supabase, cột thế hệ thực tế của bảng `members` là `generation_level`. Khi API route (`/api/kinship`) dùng `.order('generation_number')`, truy vấn SQL bị lỗi và try/catch âm thầm fallback sang dữ liệu mock (`MOCK_CLAN_MEMBERS`), khiến nhà phát triển tưởng trang đang chạy bình thường nhưng thực chất không bao giờ lấy được dữ liệu thật.
  2. *Giải pháp Chuẩn hóa 2 Tầng (Database & TypeScript Model):* Khai báo trường chính là `generation_level?: number` và `generation_number?: number` trong `Member` (`src/types/database.ts`) để tương thích ngược 100% với cả CSDL PostgreSQL lẫn các test suite cũ. Lõi `lca-finder.ts` và `regional-dictionaries.ts` đọc an toàn qua `m.generation_level ?? m.generation_number ?? 1`.
  3. *Client-Side Dynamic Fetching & 0ms In-Memory Zero Latency:* Trang `/kinship` nạp danh sách thành viên thực tế từ `/api/members` vào state `membersMap` động. Nhờ đó, việc tính toán cây họ hàng (LCA, xưng hô 3 miền, cây chữ V, trực hệ dọc) vẫn thực thi 100% in-memory trên Client với tốc độ < 1ms tức thì khi đổi dropdown hoặc bấm kịch bản mẫu, không bị nghẽn mạng hay phụ thuộc vào network request cho mỗi thao tác người dùng.
